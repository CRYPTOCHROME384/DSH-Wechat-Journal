# dsh-journal

把散在微信、AI 对话和随手笔记里的东西，**压实**成一份能读的笔记本。

DeepSeek Harness 的两个插件 + 一个本地文件层。账本和收件箱保存在本机；微信收发、网页抓取及 DSH 的模型调用需要网络服务。

---

## 它解决什么问题

碎片化信息管理的失败，通常不是因为「没记下来」，而是三件事：

1. **只进不出。** 消息、链接、想法越攒越多，从来没有一步把 N 条原始记录变成 1 条当前状态。于是「最新的到底是什么」只能靠脑子维护。
2. **每次整理都在重新设计系统。** 上一次的分类、上一次的模板，这次不用了。坐标系一漂移，累积归零。
3. **系统和你的判断混在一起。** AI 把你一句「觉得这方法有点旧」写成了项目结论，你下次看到会愣住：这是我说的，还是它编的？

这套东西的三个对应设计：**压实**（compaction）、**规则文件化**、**证据与结论分离**。

---

## 三个层次

| 层 | 是什么 | 存在哪 | 你看它的频率 |
| --- | --- | --- | --- |
| **S1 原始材料** | 聊天原文、转发、文件变动 | `capture/<日期>.jsonl` | 只在核对时 |
| **S2 当前状态** | 每个项目**现在**的样子 | `projects/<项目>.md` | 每天 |
| **S3 长期理解** | 你写下的判断、经验、未决问题 | 本子 + 项目「未决」 | 想起来才看 |

S1 可以很多，**S2 必须少**，S3 必须是自己写下来的话。

---

## 三个节奏

| 时机 | 做什么 |
| --- | --- |
| **收到消息** | 当场分诊：分类、抽时间、归位，回一句「理解成什么 + 放哪了」 |
| **每晚** | 语义收口：找「做完了 / 没改善 / 决定用 X」，关任务、更新项目状态 |
| **每周** | 压实：合并重复、改写四问、出周报 |

即时那层是**正则**，只做结构化归位；语义合并放在当晚——因为「这句话是在收尾上周那件事」需要理解，正则做不到。

## 数据流

```
微信 ──> reading-inbox 插件 ──> capture/<日期>.jsonl（只追加）
                                    │
                                    ├─ 有链接 ──> 阅读收件箱（另一套视图）
                                    └─ 无链接 ──> journal.py triage
                                                     │
                                            分诊：task / idea / ref
                                                     │
                                              store.json（结构）
                                              projects/*.md（四问）
                                                     │
                                          ┌──────────┴──────────┐
                                     面板（读写）          定时任务（收口/压实）
```

## 四条硬规则

Agent 的整理规则写在数据目录的 `RULES.md` 中；修改规则不会自动改变 Python 的正则分诊逻辑。仓库 `journal/RULES.md` 是首次安装模板。最要紧的四条：

**1. 机器绝不改写你的本子。** 会被系统改写的本子，人就不敢认真写。

**2. 项目文件里，机器只重写两个标记之间。**

```markdown
<!-- journal:managed -->
## 要解决
## 现在
## 下一步
## 未决
<!-- /journal:managed -->

## 我的理解      ← 这一段机器只读，永不碰
```

找不到标记就**拒绝改写**，绝不覆盖。

**3. 证据必须带逐字引用。** 想把一段材料写进项目进展，必须给出来源里真实存在的原话，否则闸门拒绝。文件变动只能记成「观察」，不能据此改结论。

**4. 冲突永不自动合并。** 两侧都改过，就报出来让人选。自动合并会把两个都合理的改动揉成一个都不对的版本，而你看不出它揉过。

## 安装

```
git clone https://github.com/CRYPTOCHROME384/DSH-Wechat-Journal.git
cd DSH-Wechat-Journal
node install.mjs
```

然后两件事：**重启 DeepSeek Harness**，再让 agent 按 `schedules-ready.md` 建三个定时任务（安装器会打印路径）。

默认账本目录 `~/.dsh-journal/data/`，可用 `--data` 指定。装完是**空账本**，没有任何示例数据。

详见 [INSTALL.md](INSTALL.md)。

---

## 目录

```
plugins/reading-inbox/   微信通道 + 阅读收件箱（链接、文献）
plugins/journal-panel/   账本面板（现在 / 想法 / 密度 / 本子）
journal/                 journal.py 及模块，规则文件 RULES.md
templates/               数据目录的空骨架
install.mjs              安装器（幂等）
```

`journal/` 是代码，数据目录是数据——**两者可以分开放**，安装器会把 `.py` 复制进数据目录，让数据目录自包含、可整包备份。

## 一些取舍

**不做正文的双向同步。** Markdown 和结构化块之间往返会掉格式，第一次同步就会把你写的东西改形。字段可以双向，正文只单向。

**只有三种类型**（任务 / 想法 / 资料），不新增。类型多了分类就失去意义——分类只回答「该进哪条流水线」，不负责让你「找到」东西，找东西靠搜索。

**不为收藏生成待办。** 「这篇文章挺有意思」是线索，不是任务。只有它回答了一个问题、或者你写下了理解，才值得再走一步。

**不给静默赋予含义。** 任务没勾完成不等于没做，长期没提到不等于放弃。系统只能问「要不要暂缓」，不能替你判定。
